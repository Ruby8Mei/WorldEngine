# 9.2 INOP feature security analysis and marker design audit

## Result

INOP is a historical rotor-machine experiment. It is unsuitable for protecting real secrets.

The strongest measured result is narrow: daily rotor wiring regeneration prevents the existing catalogue-based Bombe experiment from containing the true machine. The experiment does not show that regenerated wiring resists statistical recovery from traffic. The double pass imposes about a sevenfold cost on the measured classical attack path, but it remains a constant factor. Variable notch density adds no measured resistance to exhaustive start-position search. Large configuration counts are search-space arithmetic, not security claims.

The current marker is already a uniformly sampled, message-specific 16-symbol value drawn through the operating-system entropy layer. Replacing it with a deterministic value derived from settings or message content would weaken repeated-message behavior and create replay or reuse signals. The recommendation is to retain random uniqueness and change presentation only if stronger INOP identity is desired. No marker algorithm or ciphertext format is changed by this audit.

## Scope, attacker models, and evidence labels

This analysis treats the algorithm as public. Security does not depend on source secrecy or on an attacker failing to understand the pipeline.

Attacker models used below:

- **Passive traffic analyst:** sees ciphertext length, grouping, any clear language tag, and the separately transmitted marker. The analyst may compare many messages.
- **Known-machine crib attacker:** knows the wheel wirings and machine procedure, has a guessed plaintext fragment, and searches settings or crib placements. This is the model implemented by the existing Bombe harness.
- **Unknown-wiring traffic attacker:** knows the procedure but not regenerated rotor or reflector wiring and may collect traffic under one or more settings. No repository experiment implements this attack.
- **Local data attacker:** can read process output, clipboard content, or saved files under the same operating-system account. Interface validation does not resist this attacker.
- **Accidental-failure case:** wrong settings, truncated input, malformed saved data, or corrupted ciphertext. This is correctness handling, not adversarial confidentiality or authenticity.

Evidence labels:

- **Measured:** reproduced by an existing offline experiment against repository code.
- **Code-derived:** exact arithmetic or behavior follows from the implementation and stated parameters.
- **Estimate:** a model-based quantity that has not been confirmed by a dedicated attack.
- **Untested:** plausible effect or attack path with no repository measurement.

Classification labels are **cryptographic benefit**, **obscurity**, **operational friction**, **interface protection**, **lore-only behavior**, and **little to no security value**. A feature may have a primary and secondary label where its behavior crosses boundaries.

## Feature findings

### Rotor count, selection, order, and starting positions

The machine composes the plugboard, every rotor in the selected order, the reflector, the reverse rotor path, and the plugboard again for each symbol. More rotors therefore change the actual permutation rather than merely changing a label. INOP-38 accepts 5 through 10 rotors, and its master key carries one starting symbol per rotor plus one reflector orientation symbol. Evidence: `src/logic/registry.cpp:92-96`, `src/logic/inop.cpp:166-196`, and `src/logic/inop.cpp:244-264`.

The existing full-scale arithmetic uses a controlled pool of ten rotors and five selected rotors. It reports 30,240 orders, or about 2^14.88, and 38^5 starting positions, or about 2^26.24. These values apply to that attack model. Normal INOP selection now draws from generated wheel files, so the current pool size is deployment-specific and must not be silently replaced by ten in a general security claim. Evidence: `measurements/3-bombe.md`, section Full scale, and `src/logic/registry.cpp:634-660`.

The interaction with wiring knowledge is decisive. Order and starting-position counts matter only after the attacker has candidate wirings to run. The Bombe finds the key in the reduced known-wiring cell and misses it when the true wirings are absent. The unresolved paths are attacks that recover order and state without exhaustive enumeration, attacks against 6 through 10 rotors, and traffic analysis that exploits slow rotors which remain static inside ordinary message lengths.

### Rotor wiring and regeneration

A rotor wiring is a permutation of the active alphabet. The loader and constructors reject malformed permutations, duplicate wirings, and pure rotations. Generation uses an operating-system entropy source and Fisher-Yates shuffling. Evidence: `src/logic/inop.cpp:46-68`, `src/logic/generator.cpp:104-111`, `src/logic/registry.cpp:345-439`, and `cmake/check_source_rules.cmake`.

Daily regeneration has the strongest measured effect in the repository. In the reduced Bombe experiment, known wiring finds the true setup and unknown wiring returns zero survivors because the true setup is absent from the catalogue. This establishes resistance to that catalogue search only. It does not establish resistance to rotor-wiring reconstruction from many messages, depth, chosen plaintext, or captured settings. Evidence: `measurements/3-bombe.md`, section INOP-38 ablation.

The raw count of one 38-symbol rotor permutation is 38!, about 2^148.55, and five independent wirings form an arithmetic space near 2^742.76. These are not effective security levels. Rotor machines expose algebraic and statistical structure, and no repository experiment searches this space directly. The report therefore classifies regeneration as a real cryptographic benefit with a major untested attack boundary, not as a claim of hundreds of security bits.

### Ring settings

Each ring setting changes the offset used by the baked forward and reverse rotor tables. The implementation normalizes a one-based input into the alphabet range and uses position minus ring as the effective offset. Evidence: `src/logic/inop.cpp:70-91` and `src/logic/inop.hpp:73-108`.

The existing five-rotor arithmetic credits 38^4 effective ring settings, about 2^20.99, because one global degree of freedom is redundant with starting positions in the stated model. That number describes candidates an exhaustive attacker might enumerate after wirings and other structure are fixed. It is not a measured resistance result. The Bombe ablation fixes every ring to one and therefore does not isolate rings. Evidence: `measurements/3-bombe.md`, sections INOP-38 ablation and Full scale.

Rings interact with starting positions and wiring. They do not change notch locations in this implementation because notch checks index the visible rotor position directly, while ring offsets apply in the signal tables. An attack may exploit this separation. No repository experiment tests ring equivalences, ring recovery, or joint ring and start-position pruning.

### Fixed and variable notches

Legacy wheels retain historic fixed notches. INOP-38 settings carry 1 through 5 notch symbols per rotor, with duplicate symbols across the machine rejected. More notches increase turnover frequency and wake slower rotors earlier, while reducing the full stepping period. Evidence: `src/logic/registry.cpp:76-96`, `src/logic/generator.cpp:129-159`, `src/logic/generator.cpp:189-216`, and `src/settings/settings.cpp:118-132`.

The measured notch sweep is flat. Across 1, 2, 3, 4, and 5 notches per rotor, run times stay between 2.99 and 3.07 seconds and every cell finds one survivor. More motion inside a message does not cost an exhaustive start-position attacker more in that harness. The code records a separate motion observation: over 1,000 symbols, moving from 3 to 5 notches takes rotor 3 from 7 visited positions to 18 and rotor 4 from about half a step to two, while later rotors remain still. That motion observation is not an attack result. Evidence: `measurements/3-bombe.md`, section Notch density sweep, and `src/logic/registry.cpp:76-91`.

Variable notches remain configuration material and may obstruct an attack that assumes known turnover. No such attack is measured. The current justified benefit is operational behavior and extra configuration variation, with no measured security gain against the implemented attack.

### Reflector choice, wiring, orientation, and motion

The reflector is validated as a fixed-point-free involution. This makes the single-pass machine reciprocal and prevents a symbol from directly enciphering to itself. The same property historically enables free crib-placement rejection, so it is both functional and structurally exploitable. Evidence: `src/logic/inop.cpp:110-138` and `measurements/3-bombe.md`, section Crash elimination.

A general 38-symbol fixed-point-free involution has an arithmetic space near 2^72.80. Reflector choice from a known finite pool adds only the logarithm of the pool size. Reflector wiring regeneration could be more significant, but it has not been isolated from rotor regeneration in an unknown-wiring recovery experiment.

INOP also keys the initial reflector orientation and advances it on a 37-step counter against the 38-position fast rotor, so the combined cycle is 1,406 positions. The initial orientation contributes 38 candidates, about 2^5.25, in the existing full-scale arithmetic. This is code-derived state, not measured resistance. Evidence: `src/logic/inop.cpp:188-198`, `src/logic/inop.cpp:226-241`, and `measurements/3-bombe.md`, section Full scale.

Unresolved gaps include whether reflector motion introduces exploitable periodic relations, how much independent value orientation retains after other state is normalized, and whether regenerated reflector wiring can be reconstructed from traffic.

### Plugboard size and configuration

The plugboard accepts disjoint symbol pairs and applies the same involution before and after the rotor path. INOP-38 allows up to 15 pairs. Validation prevents self-pairs, symbols outside the alphabet, and reused symbols. Evidence: `src/logic/inop.cpp:141-164`, `src/logic/registry.hpp:12-24`, and `src/settings/settings.cpp:133-143`.

The existing arithmetic gives about 2^78 configurations for exactly 15 pairs on a 38-symbol alphabet. This can make naive enumeration infeasible, but it is not an effective security-bit claim. Historic Bombe methods do not enumerate every plugboard directly. They propagate pair assumptions and contradictions, which is why the missing steckered and diagonal-board stage matters. Evidence: `measurements/3-bombe.md`, sections Full scale and What was not built.

The plugboard is classified as a cryptographic benefit with an unresolved central attack path. No repository result measures the difference among zero, partial, and 15-pair configurations against a steckered attack.

### Double pass

Each pass rewinds to the same machine state. With the option enabled, INOP enciphers once, swaps the two body halves, rewinds, and enciphers again. This preserves reciprocal operation while breaking the direct relationship that every single-pass reflector machine symbol differs from the plaintext symbol at the same position. Evidence: `src/logic/pipeline.cpp:103-124`.

The measured known-wiring crib search takes 13.54 seconds with the double pass and 2.90 seconds without it, or 4.65 times more work per candidate in that cell. Crash-elimination measurements show that a 16-symbol crib loses a free filter worth about 34 percent of placements, and applying that filter anyway discards the true placement in 33.5 percent of trials. Together the report gives a rough sevenfold cost for this attack class. The known-wiring truth is still recovered. Evidence: `measurements/3-bombe.md`, sections INOP-38 ablation and Crash elimination.

The benefit is real but bounded. It taxes the tested attack and disrupts a classical assumption; it does not create modern diffusion, authentication, or a hardness reduction. The steckered attack path remains unimplemented.

### Half-swap and reversal behavior

The current transposition swaps the two equal halves. It is an involution with no fixed index for an even-length body. The previous reversal was also an involution, but an odd-length body left its center index fixed, causing the two identical per-position passes to cancel at that known position. Encryption now forces even length before the half-swap. Evidence: `src/logic/pipeline.cpp:58-90` and `src/logic/pipeline.cpp:139-149`.

The transposition sweep measures reversal and half-swap at effectively identical cost, with all runs near 13.5 seconds and the true key recovered. The supported claim is therefore only that half-swap removes the old fixed-index defect. No broader attack cost is demonstrated. Evidence: `measurements/3-bombe.md`, section Transposition sweep.

### Padding and cover traffic

With padding enabled, the pipeline places the same marker on both sides of preprocessed plaintext, then adds random cover symbols before and after the marked body. Noise is the greater of 64 symbols or 35 percent of the marked message length, rounded so total output aligns to the configured block. The front and back split is random. Evidence: `src/logic/pipeline.cpp:43-56` and `src/logic/pipeline.cpp:125-149`.

This hides exact boundaries and makes short ciphertext length less directly proportional to plaintext length. It does not hide that output length grows with message size, and block alignment reveals a length interval. A passive analyst can compare repeated traffic volumes. The cover symbols do not provide integrity and are removed only by marker search after decryption.

The existing Bombe analysis deliberately disables padding and uses fixed body lengths. No measurement shows how much padding impedes crib discovery, statistical recovery, or traffic analysis. Its current classification is operational friction and obscurity, not quantified cryptographic strength.

### Markers

The default marker is 16 independent symbols drawn uniformly from the active alphabet by `secure_string`. For INOP-38 this gives 38^16 possible values, about 2^83.97. A specified pair of independent markers collides with probability 38^-16, about 5.29e-26. The approximate 50 percent birthday scale is 5.12e12 generated markers. These are code-derived ideal-source calculations, not measured claims about whole-system security. Evidence: `src/logic/pipeline.hpp:14-28`, `src/logic/pipeline.cpp:125-134`, and `src/logic/rng.cpp:83-101`.

After deciphering the full body, `carve` uses the first and last occurrence of the supplied marker and returns the text between them. Missing or single marker occurrence throws. A wrong key usually fails because two marker copies are not recovered, but the mechanism is not an authenticator. A wrong key or modified ciphertext can in principle produce two matches, and corruption outside both recovered markers can be silently discarded as cover traffic. Evidence: `src/logic/pipeline.cpp:92-99` and `src/logic/pipeline.cpp:154-173`.

The marker is transmitted separately and the GUI can copy it alone or together with ciphertext. Anyone who sees the dispatch can normally see the marker. It protects no secret and proves no sender identity. Its benefit is reliable boundary recovery under random cover traffic and a low accidental-match rate.

Marker interactions and gaps:

- Marker length depends on suite configuration but no format version travels with the ciphertext.
- A marker occurrence inside plaintext or random cover can change which boundaries `find` and `rfind` select. Under an ideal uniform body, a union-bound estimate is the number of candidate windows divided by 38^16. Real plaintext is not uniform, though the random marker is independent of plaintext.
- There is no dedicated corruption test that mutates symbols inside, outside, and across marker boundaries and measures detection behavior.
- Legacy locks padding off, so it emits no marker. Evidence: `src/logic/pipeline.cpp:10-19`.

### Transformer and language metadata

The transformer is an operational encoding layer that carries supported Unicode text through the 38-symbol machine alphabet. It is outside the cipher core. The clear three-letter language tag is appended to terminal ciphertext for interface context and stripped before deciphering; it does not select a different cryptographic key. Evidence: `src/interface/main.cpp:1734-1754`, `src/interface/main.cpp:2051-2073`, and `src/interface/gui_enciphering_panel.cpp:225-234`.

Measurements show that the universal fold grammar removes 0.3015 bits per transmitted symbol from the unconstrained 38-symbol space. Ordinary order-1 language structure gives away about 2.106 bits per symbol in the same corpus model, roughly seven times more. Folded text is less predictable per original character than accent-stripped text in all 48 measured languages, by up to 0.9924 bits. Moving mark data into a trailer costs more total bits for 41 of the 48 languages that carry marks. Evidence: `measurements/1.2-marginal-predictability.md` and `measurements/1.3-search-space.md`.

Mark distributions alone classify language with 66.1 percent accuracy at 500 characters and 72.9 percent at 2,000, while letters alone already reach 91.8 percent at 500 characters. The scheme leaks language features, but language itself leaks more strongly through ordinary letter frequencies. The clear tag removes any need to infer it for an observer. Evidence: `measurements/1.4-language-fingerprint.md`.

Keyed table recovery is mixed: Czech recovers every tested digit permutation at a mean of 740 characters under a matched reference profile, while Cantonese and Mandarin do not recover within the available windows. This is not a general proof for or against keyed encoding tables. Evidence: `measurements/1.5-permuted-table-recovery.md`.

### Setup generation and entropy checks

On Windows, random bytes come from `BCryptGenRandom` with the system-preferred generator. Other platforms use `/dev/urandom`. Failure throws and there is no fallback to `rand` or `std::random_device`. `secure_below` rejects the biased tail, and `secure_string` does the same for alphabet sampling. The build scans logic, settings, and interface sources to enforce the RNG rule. Evidence: `src/logic/rng.cpp:1-101` and `cmake/check_source_rules.cmake`.

Entropy health checks sample raw-byte coverage, chi-square, bit balance, and 38-way draw coverage before setup, key-sheet, and wheel generation paths. Generated wheel batches are then checked for duplicates, pure rotations, permutation validity, reflector invariants, and safe replacement behavior. Evidence: `src/logic/rng.cpp:107-190`, `src/logic/generator.cpp:237-247`, `src/logic/generator.cpp:263-351`, and `src/logic/generator.cpp:484-519`.

These checks reduce implementation and catastrophic-source risk. They do not prove that the operating-system source is unpredictable, detect every compromised source, protect random values after persistence, or convert the rotor machine into a modern cipher. The feature is a necessary cryptographic hygiene measure rather than evidence of end-to-end security.

### Key and preset persistence boundaries

Settings, setup presets, key sheets, rotor catalogues, and reflector catalogues are persisted as JSON. Settings and presets include the master key and other complete configuration fields in plaintext. Readers validate structure and machine constraints before use, and migration refuses to overwrite an existing modern target with a legacy source. Evidence: `src/settings/settings.cpp:93-150`, `src/settings/settings.cpp:251-304`, `src/interface/gui_config_store.cpp:30-62`, and `src/logic/generator.cpp:452-519`.

The confidentiality boundary is the operating system account and file permissions. The application adds no encryption at rest, password protection, file authentication, secure deletion, or dedicated permission hardening. Migration can deliberately preserve an old source, which is correct for recoverability but may leave another sensitive copy. The terminal also displays active settings including the master key, and the GUI master-key field is an ordinary visible text field. Evidence: `src/interface/main.cpp:356-394` and `src/interface/gui_setup_panel.cpp:530-552`.

Validation is interface protection. It prevents malformed settings from selecting an unintended machine, but it does not prevent a local reader from learning the settings or a local writer from replacing a valid file with another valid file. Saved compatibility also depends on preserving the exact generated wheel material. A saved name without its matching catalogue is not a recoverable key.

### Interface protections that may look security-relevant

The interface filters ciphertext and marker input to the active alphabet, validates setup fields, refuses missing markers for padded messages, rejects odd ciphertext length under the double pass, and locks modern options off for the historic suite. Save flows include validation and overwrite gates. The README states that the program is not a security product. Evidence: `src/interface/gui_enciphering_panel.cpp:183-197`, `src/interface/gui_enciphering_panel.cpp:225-255`, `src/interface/gui_setup_panel.cpp:150-218`, `src/logic/pipeline.cpp:154-169`, and `README.md:3-8`, `README.md:48-52`.

These controls prevent operator errors and preserve procedure consistency. They do not hide the key from the display or clipboard, authenticate ciphertext, authorize users, constrain filesystem readers, or mitigate memory inspection. Historic locks are lore and compatibility behavior, not added security.

## Claims corrected or downgraded

1. **Search space is not security strength.** The 2^67.36 known-wiring setting space without plugboard and the much larger spaces with plugboard or regenerated wiring are arithmetic under an exhaustive model. Rotor-machine structure may permit much cheaper attacks.
2. **Daily regeneration stops only the implemented catalogue search.** It has not been tested against wiring recovery from depth, many messages, chosen plaintext, or captured procedures.
3. **The double pass is a tax, not a wall.** The supported headline is roughly sevenfold cost for the measured classical path, with known-wiring recovery still successful.
4. **More notches do not add measured resistance to exhaustive start-position search.** They change internal movement, but the measured curve is flat.
5. **Half-swap is not stronger than reversal in measured search cost.** Its justified improvement is removal of the odd-length fixed index.
6. **Padding and markers are not authentication.** Marker failure is useful error detection, but accepted output is not proof of an untampered ciphertext or correct sender.
7. **Language transformation is not a security layer.** Its grammar leaks some structure, ordinary language leaks more, and a clear tag discloses the selected language directly.
8. **Entropy checks protect generation quality, not the rotor construction.** Strong random input cannot provide modern diffusion, authenticity, forward secrecy, or professional review.

## Lore-consistent marker investigation

### Operational meaning of purely INOP-encoded

A meaningful definition must say what information enters the procedure, what state is required, and what the receiver transmits or reconstructs. Four interpretations are possible:

1. **Settings-derived marker:** encode rotor names, positions, rings, notches, or reflector state into marker symbols.
2. **Message-derived marker:** encode plaintext, ciphertext, or length through an INOP procedure.
3. **External serial or time marker:** encode a counter, date, message number, or operator group in the INOP alphabet.
4. **Random seed with INOP presentation:** retain an independent random value, then apply a specified INOP-era presentation or naming convention without changing its uniqueness requirement.

Only the fourth interpretation preserves the central property of the current design without introducing state or deterministic reuse. Running a uniform random marker through any fixed reversible INOP transformation leaves it uniformly distributed. That changes lore or presentation, not security.

### Candidate design audit

| Candidate | Uniqueness and collision behavior | Leakage and replay | Boundary recovery and failure behavior | Compatibility | Security effect |
|---|---|---|---|---|---|
| Current random 16-symbol marker | 38^16 space and independent per message under the ideal source model | No deterministic repeated-setting signal | Receiver supplies marker; two plaintext-boundary copies must be found | Current behavior | Baseline operational reliability |
| Marker derived only from settings | Repeats whenever settings repeat | Directly links traffic under repeated settings and enables replay of the boundary value | Receiver can derive it before decryption, but wrong settings may derive a different marker and fail ambiguously | Could remove transmitted marker only with a new procedure and format rule | Removes security and operational privacy |
| Marker derived from plaintext or ciphertext | Deterministic collisions follow repeated content or digest truncation | Links repeated messages or prefixes; ciphertext-derived variants can be circular because decryption needs the marker to locate plaintext | Plaintext derivation is unavailable before carving; ciphertext derivation must define corruption behavior | Requires a new algorithm identifier and likely breaks old traffic | Removes privacy and adds complexity |
| Encoded time or counter | Unique only if clocks or persistent counters never reset, race, or clone | Reveals timing or sequence and supports traffic correlation | Receiver needs the same external state or the encoded value must travel with the message | New state and recovery rules required | Operational trade, no cryptographic gain |
| Random value passed through a reversible INOP procedure | Same collision behavior as current marker if the input remains uniform and independent | No added deterministic reuse, but no hidden security benefit | Receiver can use the presented marker if it is exactly the boundary value; extra inversion steps add failure modes | Can preserve length and alphabet, but old and new procedures still need identification if reconstruction differs | Lore-only change with possible implementation risk |
| Random value with presentation-only terminology | Exactly current behavior | Exactly current behavior | Exactly current behavior | Full compatibility | Lore-only behavior, no security change |

### Determinism and reuse findings

A marker derived solely from machine settings is identical for every message under those settings. Since the marker is separately transmitted, an observer can group messages by marker even before cryptanalysis. If the marker is omitted and reconstructed, a repeated setting still creates the same internal delimiter and the procedure becomes dependent on perfect external setting synchronization.

A marker derived from plaintext cannot be known until the plaintext has already been located, which is circular under the current `carve` design. A marker derived from ciphertext can be calculated before decryption, but a single ciphertext edit changes the derived value and makes failure behavior dependent on the derivation. Neither option provides authenticity unless a modern keyed authenticator is introduced, which is outside this project and explicitly outside the cipher core.

Counters and time values can avoid immediate repetition only with durable state, collision rules, reset handling, and multi-process coordination. Encoding such a value through rotors does not hide its small or predictable source space from a public-algorithm attacker. It also creates recovery dependencies that the current stateless random marker avoids.

### Boundary location, wrong keys, and corruption

Current decryption first reverses the one-pass or two-pass machine procedure and then searches the resulting body for the supplied marker. Both boundary copies are not found by scanning ciphertext directly. Any replacement must result in the exact same marker string at both plaintext boundaries or must replace `carve` with a versioned framing format.

Current failure cases are:

- Empty marker with padding enabled: explicit refusal.
- Odd ciphertext under double pass: explicit truncation refusal.
- Zero or one marker occurrence after decryption: explicit wrong-setting or corruption refusal.
- Two or more occurrences: first and last define the returned body, even if extra occurrences came from plaintext, cover traffic, a wrong key, or corruption.

This is useful correctness checking but not reliable tamper detection. A lore design must not claim that deterministic reconstruction improves this property.

### Compatibility, length, and alphabet

Existing ciphertext carries no marker-version identifier. The receiver accepts an arbitrary marker string from the active alphabet and expects the operator to provide the matching value. Keeping the current 16-symbol alphabet-bound value preserves stored ciphertext, copy and paste behavior, batch procedures, and failure messages.

Changing length changes accidental-match arithmetic and may affect interface assumptions. Adding symbols outside the suite alphabet fails current input filters. Eliminating the transmitted marker requires a new reconstruction rule and creates an old-versus-new ambiguity. A future non-presentation change therefore needs an explicit procedure version and backward decryption path.

### Recommendation

**Retain random uniqueness but change presentation only.**

Keep the operating-system entropy draw, 16-symbol default length, active alphabet, two boundary copies, separate dispatch value, and current decryption contract. If stronger identity is desired in a later job, rename the visible concept to an INOP-specific term such as boundary indicator and document it as message procedure. Do not derive it from settings, plaintext, ciphertext, time, or a counter. Do not move marker generation into `src/logic/inop.hpp` or `src/logic/inop.cpp`.

Passing the random value through a reversible rotor procedure is not recommended because it produces the same uniform distribution while adding state and compatibility risks. A terminology and presentation change delivers the lore benefit honestly without pretending to add cryptographic strength.

## Unresolved evidence gaps

- Unknown-wiring recovery from many messages, repeated settings, depth, known plaintext, or chosen plaintext.
- A steckered Bombe or diagonal-board attack that measures actual plugboard resistance.
- Joint search and equivalence analysis for rings, start positions, reflector orientation, and rotor order.
- Attack impact of 6 through 10 rotors rather than the reduced three-rotor experiment and five-rotor arithmetic.
- Attacks that exploit slow-rotor stasis and the 1,406-step rotor-reflector cycle.
- Padding impact on crib discovery, length inference, and traffic analysis.
